# Develop the brain through use

Treat setup as a starting point. Help the person develop a structure that earns its place through their work, using the existing components rather than a parallel maintenance system. Apply the local rules, source boundaries, and approval gates throughout.

## Open the right door

| What the person needs | Start with |
|---|---|
| "Where should this live?" | Read the folder map and relevant hub; favor leaving it in place, a hub entry, or a cross-reference. Use ingest only for durable reference synthesis. |
| "What could I build next?" or "Help me explore my setup" | Read the purpose, index, relevant project status and open questions. Identify one useful task or ask one question about an actual difficulty. |
| A new project or a changed role | Use setup for a targeted extension to the existing brain, preserving what already works. |
| The same explanation or correction keeps coming up | Check the relevant sources and corrections; ask whether this is a durable fact, a standing preference, or an exception for this task. |
| A useful lesson from finished work | Offer capsule if the person wants to preserve the reasoning; follow its deliberate-invocation boundary. |
| Stale, conflicting, or hard-to-find material | Use health-check at the scope that fits; its approval process owns repairs. |
| Work that will continue later | Use handoff, pointing to saved context rather than repeating it all. |

For a concrete task, do that task first. An optional improvement can follow if it addresses observed friction. A general exploration request is permission to inspect relevant files within the agreed brain, not every file on the device. If the folder or goal is unknown, ask before inspecting. If the host lacks access, explain what is unavailable and work from supplied context without claiming an inspection.

## Work through one improvement

1. **Find evidence.** Read local rules, then only the index, project files, corrections, capsules, or log entries relevant to the request. Cite the files or the person's current statement behind the observation. If repeated friction is not in the available evidence, describe a possibility and ask; never invent a usage history or infer preferences from timestamps or silence.
2. **Clarify the useful outcome.** Ask one question if needed, such as "What do you find yourself having to explain again?" or "Which part is hardest to find?" Reuse facts already supplied. Keep the conversation about their work before naming folders.
3. **Offer a small choice.** Give up to three concrete options with tradeoffs, including using the current structure when it works. Favor one small reversible change over a new taxonomy or dashboard. Show the relevant path and a short example of the result. Distinguish a hypothesis from a confirmed need.
4. **Agree what should persist.** Confirm standing preference wording before saving it. A task-specific request applies to the task; it does not become a permanent rule by inference. Show proposed structural or rules changes and honor existing approval gates. An explicit request to create a named project may authorize those additions; it does not authorize moving existing notes. Keep declined suggestions out of standing rules.
5. **Apply through the owning component.** Use setup for approved additions, ingest for qualifying reference knowledge, health-check for repairs, capsule for requested finished-work reasoning, and handoff for continuation. Plain placement advice can end without invoking a component or writing a file. Record accepted structural/rule changes with reason and date in the existing change log; use existing project status for trial actions. Preserve immutable sources and repair affected links.
6. **Check the benefit.** Verify changed paths and links; run the bundled checker when structure or links changed. Try the question or task that motivated the change, with citations. If a fresh session is needed to establish the benefit, label that check pending until observed. For a trial, agree what would make the person keep or reverse it; retain prior versions under the local revision rules.

End with what changed, what remains a proposal or trial, and one practical next action. If no change is useful, say so and continue using the brain. A successful development conversation can produce advice without producing more files.

## Make exploration routine without making it intrusive

After first useful setup, offer a choice between doing more real work and exploring one next improvement; do not restart the interview. When the user signals confusion, a new kind of work, or a recurring problem, connect that signal to one relevant option above. During a standard upkeep visit, health-check can ask whether the structure still fits their work even when its mechanical checks are clean. Honor a preference to keep these invitations on request only. A quiet project or a single unusual request is not enough evidence for redesign.

The durable adaptation lives in confirmed local rules, source-backed notes, corrections, project status, and requested capsules. Future sessions read those artifacts; the model is not being retrained. Keep that continuity visible by pointing to a relevant saved decision when it helps, rather than claiming to know the person beyond the available record.
